# Native webfetch settlement boundary

The requested error-to-portable-delivery fix is **blocked by the installed native lifecycle contract**. No runtime continuation was added. OpenCode 1.18.26 can publish a terminal webfetch error while a response body is still being transferred. Even its ordinary `Transport error (GET URL)` envelope does not identify a safe subset: it also occurs after the tool's internal Cloudflare-challenge retry while the first response remains active.

This is a reproduced technical limit, not a claim that every transport failure leaves active work. A single refused/broken connection can settle cleanly, but the workflow callback cannot distinguish that path from the counterexample. The controlled server has observations the production plugin does not have. Resource cleanup is timing-dependent: an initial challenge/transport run retained an active response, while its stricter rerun found that response closed by the delayed sample. Both outcomes are retained; the latter is not evidence of a completion guarantee at error publication. Using test-server knowledge as a production continuation criterion would manufacture evidence.

## Installed contract

The unmodified Linux executable reports 1.18.26 and SHA-256 `096d32aa9778f98981390a0602c1f8af55ee5f1d6d5c58206f8fb2743c90eafe`. [Source slice offsets and hashes](source-slices.json) identify the minified code read directly from that executable, not an assumed current upstream version.

1. The legacy native `webfetch` used by the tested AI SDK path validates the URL, awaits `ask(permission: webfetch)`, then executes an HTTP GET. Permission rejection precedes the request.
2. `filterStatusOk` rejects non-2xx responses before `arrayBuffer` is read. A 403 with `cf-mitigated: challenge` invokes a second request with User-Agent `opencode`. This is existing OpenCode behavior; the harness adds no retry.
3. The configured timeout wraps request execution/status filtering, **not the later array-buffer read**. Size rejection may also happen before reading the body. Timeout/size/error strings therefore cannot certify body completion.
4. The HTTP client wraps successful response objects with an abort controller. Unconsumed responses are registered for finalization; body access unregisters that fallback and installs interruption handling. Non-2xx rejection is not an awaited body-consumption/cancellation finalizer.
5. `SessionProcessor.failToolCall` records the error string and start/end times from a running part. It exposes neither the internal request count nor a response-settlement receipt. Normal rejection of the tool effect confirms that effect returned; it does not certify cleanup of all responses created inside it.

Matching admission, current session/callID/arguments, ordered native time, unchanged snapshots and an exclusive queue are necessary but insufficient here. In the challenge/transport counterexample they all coexist with an active response. Waiting for silence, relying on garbage collection, inspecting only terminal parts or treating 401/403 as policy denial would not close the gap. Cancellation/deadline still stops; local cancellation does not establish remote server completion.

## Reproduction and controls

Run `node scripts/run-native-webfetch-installed.mjs` from the worktree. It uses the existing pinned Linux image and executable, `--network none`, loopback HTTP plus scripted provider, read-only mounts/root, and existing offline dependencies. No package installation through the network, public endpoint, real provider, model campaign, probe or session resumption is involved. `WEBFETCH_MODES` selects bounded scenarios.

The passive observer only records real hook/event arguments. It does not synthesize an error, wrap/replace fetch, change permissions or modify OpenCode. The bare-native diagnostic modes deliberately expose error receipt before any harness cancellation. Final-script exit success validates the native error/lifecycle observations; only `counterexample: observed` establishes overlap in that particular run; their results are not passed off as a repaired workflow. The baseline modes use the actual materialized plugin.

The source/runtime hash is checked against each materialized bundle. [Installed summary](installed.json) retains selected native events, real error receipts and HTTP counts, not full provider streams. Initial boundary scenarios ran first; baseline/control scenarios ran after the fixture's passive-observer registration and initial `$schema` configuration were corrected. A URL-specific session PermissionRuleset deny rule was also required: a blanket deny removes webfetch from the native tool inventory and tests an unavailable-tool error instead. The file-config schema rejects URL patterns for webfetch, so the deny control uses the installed SDK's `/session` `permission: PermissionRuleset` field, already used by this project. These fixture corrections were not model attempts or product fixes. A strict streaming rerun counts only write callbacks without an error. Its HTTP case reproduced the overlap; its challenge case failed the still-open-at-240-ms assertion. That challenge case was not retried. The final diagnostic script reports `observed` versus `not-observed` instead of requiring nondeterministic garbage collection to leave a response open. A non-observation is not a settlement pass. The final HTTP and session-rule deny controls run that diagnostic version; the revised challenge measurement is NOT RUN.

The response-close entries in the initial successful counterexample records were appended during explicit fixture cleanup, after the assertions and error receipt; they are not completion receipts available at the error boundary. These are active unfinished HTTP bodies, not idle keep-alive sockets. Server-side write callbacks alone do not prove application consumption; they are combined with the open response/socket and the installed non-finalizing error path. No claim is made about completion on an arbitrary remote server.

## Scope and remaining work

No supported ordinary-webfetch-error continuation is added. Successful webfetch keeps its existing path; HTTP/connection errors, native denial/reject, incomplete operations, mismatched admission, cancellation and deadlines retain the existing fail-closed behavior. Error events remain errors. File-tool recovery, bash-denial allowance, observation staleness/change history, queueing and workflow isolation are unchanged.

The requested **error → same author → local implementation/test → checks → normal terminal patch → ordinary clone** path remains unimplemented and unverified. A successful-webfetch control, a bare native error receipt and passing unit tests do not satisfy it. The prerequisite is a trusted native observation that all requests and response bodies for the call are settled before error publication, including internal retry and timeout paths. That observation is not available in the existing callback contract; changing installed OpenCode or adding a separate transport-observation mechanism is outside this assignment.

The extended proposed-continuation matrix (webfetch-specific admission mutations, queued writer races, cancellation/deadline races and two-workflow mixing) is NOT RUN as acceptance for a fix: there is no continuation branch to validate. Existing lifecycle/queue regressions are run separately. No full platform matrix, manual Actions, full verifier, containment diagnosis, merge, release or default change is claimed. `PROCESS_CONTAINMENT_UNAVAILABLE` remains outside scope. Scripted fixture behavior says nothing about Luna's ability to choose the right next action or about model-quality improvement.
